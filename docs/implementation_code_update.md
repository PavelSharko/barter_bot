# Техническая реализация: Услуги и Редактирование профиля

В этом документе описывается, как именно реализованы новые изменения в коде (архитектура, новые сущности и методы) для работы с множественными услугами и безопасным редактированием анкеты. Документ отражает всю механику рассылки уведомлений, работы с состояниями и кэшированием (Store).

---

## 1. Изменения в структурах данных (Entity)

### 1.1 Новые поля пользователя в `Enums_entity.py`
- Добавлено поле `UserProfileFields.SERVICES`, которое пришло на замену старым плоским полям `PRODUCT_NAME`, `PRICE` и `DESCRIPTION`. Поле хранит массив словарей формата `{"name": "...", "description": "...", "price": "..."}`.
- Добавлен временный контейнер `UserProfileFields.TEMP_SERVICE` для пошагового сбора данных одной услуги в FSM (Сначала `name`, затем `description`, потом `price`).

### 1.2 Новые статусы и флаги в `Enums_entity.py`
- `UserLifecycleStatus.TIMELY_PROFILE_CHANGE_BLOCKED` - Статус клиента, чья анкета находится в зоне модерации (запрещает обрабатывать его как исполнителя в сделках в `main_menu_handler.py`).
- `UserFlags.CHANGES_PROFILE_CONFIRMED` (`ChangesProfileStatus`) - Состояния проверки профиля модератором (`WAITING_CONFIRMATION`, `CONFIRMED`, `PENDING_CHANGES`, `NOT_CHANGES`).
- `UserFlags.NOW_IS_TRY_CHANGING_PROFILE` - Булевый флаг блокировки:
   - `True` = Пользователь сейчас активно редактирует анкету или переделывает ее после отказа модератора;
   - `False` = Пользователь не редактирует её прямо сейчас (Анкета отправлена на проверку модератору и ждет аппрува).

## 2. Менеджер Временных Профилей (`temp_profile_manager.py`)

Основная логика Сэндбоксинга (редактирования без мутации) вынесена в `services/users_utils/temp_profile_manager.py`.

### 2.1 Топология хранения `temp_profiles.json`
Вместо перезаписи основного файла, черновики лежат в отдельном файле `temp_profiles.json`. Запись каждого пользователя выглядит так:
```json
{
  "editing": { ... профиль в процессе редактирования ... },
  "new":     { ... замороженный профиль, ожидающий модерации ... },
  "old":     { ... копия оригинального профиля до правок ... }
}
```

### 2.2 Жизненные циклы и методы
1. **copy_profile_to_temp()**: Вызывается при нажатии "редактировать" (`edit_profile_handler.py`). Копирует данные из `UserProfile.json` в `editing` черновик.
2. **update_temp_profile()**: Позволяет точечно обновлять поля в `editing`.
3. **freeze_temp_profile()**: При нажатии "Завершить редактирование". Перемещает текущий `editing` профиль в `new`, сохраняет изначальный в `old` и удаляет `editing`. Устанавливает статус модерации. Сравнивает данные; если изменений нет — сбрасывает процесс и кидает `bot.message.answer("Вы не внесли изменений...")`.
4. **unfreeze_temp_profile()**: Если модератор отклонил профиль, происходит разморозка: данные из `new` перекладываются обратно в `editing` для того, чтобы пользователь мог продолжить работу над ошибками без потери данных.
5. **apply_new_profile()**: Если модератор принял правки — данные перезаписывают основной профиль `UserProfile.json`, а временная запись удаляется. Посылается: `"✅ Ваши изменения в анкете подтверждены модератором! Профиль обновлён."`
6. **delete_temp_profile()**: Полный сброс (используется при "Отменить изменения"). Шлёт: `"Изменения отменены. Ваш профиль не был изменён."`

## 3. Обработчики (Handlers)

### 3.1 Паттерн Фасад для FSM (`edit_services_handler.py`)
Так как создание, редактирование и удаление услуг требует работы со состояниями FSM на лету, внедрена архитектура **Facade**:
- Реализованы фасады `facade_add_service_input` и `facade_edit_service_input`.
- Эти функции берут на себя обертку сообщений: гарантируют, что временная услуга (`TEMP_SERVICE`) корректно собирается по частям в `FSMContext` и лишь в самом конце, после ввода цены, зашивается в список `SERVICES` временного профиля (`temp_profiles.json`).
- Встроена проверка отмены: вызов `check_cancel_input()` присутствует как первый шаг любого инпута, обеспечивая полную очистку состояний (`state.clear()`) при нажатии на "отмена".

### 3.2 Логика Сделок (`main_menu_handler.py`)
При нажатии "Согласен на условия" (`ACCEPT_TERMS`) внедрен блок **проверки модерации исполнителя**. Это делается ДО блокировки баланса через `add_blocked_balance`, чтобы сбежать от коллизий монет.
Логика условий:
* Получаются данные исполнителя (`provider_data.get(UserFields.STATUS)` и флаг `NOW_IS_TRY_CHANGING_PROFILE`).
* **Если статус `TIMELY_PROFILE_CHANGE_BLOCKED` и `NOW` == `False` (Анкета на проверке)**:
    - `bot.send_message` Заказчику: "Пользователь находится в стадии проверки анкеты модератором..."
    - `bot.send_message` Исполнителю: "Пользователь @[имя] пытался запросить с вами сделку, но вашу анкету сейчас проверяет модератор..."
    - `bot.send_message` Модератору (`config.MODERATOR_CONTACT_ID`): "Пользователь @[имя] пытался запросить сделку с @[имя]... Возможно стоит ускорить процесс..."
* **Если статус `TIMELY_PROFILE_CHANGE_BLOCKED` и `NOW` == `True` (Анкета в активном редактировании)**:
    - `bot.send_message` Заказчику: "В данный момент пользователь редактирует свою анкету, либо находится в стадии исправления ошибок..."
    - `bot.send_message` Исполнителю (с `⚠️⚠️⚠️ Внимание!`): "Пользователь @[имя] пытался запросить с вами сделку, но вы сейчас редактируете анкету или не завершили исправление ошибок!"
    - Модератор *не* уведомляется.

### 3.3 Действия модератора (`moderator_actions.py`)
- **Формирование диффа:** Механика `build_diff_text()` (в `temp_profile_manager.py`) генерирует безопасный html-блок для заявки админа: "Было -> Стало".
- **Принятие (`process_accept_changes`)**:
  - `apply_new_profile(target_user_id)` 
  - Меняем статус `UserLifecycleStatus.CLIENT` + `ChangesProfileStatus.NOT_CHANGES`. 
  - Отправка: `"✅ Ваши изменения в анкете подтверждены модератором! Профиль обновлён."`
- **Отклонение (`process_rejection_changes_reason`)**:
  - `unfreeze_temp_profile(target_user_id)` (Сохраняем труд).
  - Стейт флагов: `NOW_IS_TRY_CHANGING_PROFILE: True` (разрешаем продолжать), `CHANGES_PROFILE_CONFIRMED: PENDING_CHANGES`.
  - Заказчику отправляется уведомление `"🚫 Ваши изменения профиля отклонены модератором.\nПричина: {reason}..."` + клавиатура `get_still_editing_keyboard()`.
  - Модераторское сообщение апдейтится: `bot.edit_message_caption` / `bot.edit_message_text`, добавляется приписка `🚫 ИЗМЕНЕНИЯ ОТКЛОНЕНЫ\nПричина: {reason}`, а инлайн кнопки принятия/отклонения удаляются `reply_markup=None`.

### 3.4 Перехваты в Global Message Fast Store (`state_bot/global_store.py`)
Все диалоги и сообщения-заглушки во время редактирования добавляются в `global_msg_fast` (`add_message()`), что позволяет при отмене, возврате или успешном завершении очищать чат пользователя прозрачно для него (`await clear_messages(user_id)`).

## 4. Клавиатуры (`creator_inline_keyboards.py` & `edit_profile_keyboards.py`)
- В поиске на витрине `get_find_service_keyboard()` закомментировано исключение `user_status == TIMELY_PROFILE_CHANGE_BLOCKED`. Это позволяет юзерам оставаться видимыми для просмотра их профилей и чтения отзывов, перекладывая фильтр из списков прямо в точку транзакции (`ACCEPT_TERMS`).
- **Списки услуг**: Новые кластеры клавиатур (`get_service_edit_keyboard`, `get_services_footer_keyboard`). Они динамически обрабатывают `callback_data` с индексами (например: `edit_service_0`, `delete_service_4`).
- **Блок ожидания**: Имплементирована `get_still_editing_keyboard()` с кнопками: «Вернуться в меню редактирования», «Закончить редактирование» и «Отменить изменения ❌» для обработки отклоненных модератором анкет.
- Встроен "мягкий" Cancel (`get_cancel_keyboard()`) во всех шагах FSM на добавление и редактирование суб-услуг.
